## 현재 상태 진단

- 동글은 순천대 총동연 기준 단일 학교 서비스다.
- 정보 조회(목록/상세/활동보고서/일정)와 운영(회장·총동연 관리)은 갖춰져 있다.
- 학생이 "행동"할 수 있는 기능이 없다. 탐색 → 관심 → 지원 흐름 중 탐색에서 끊긴다.

## 모집 기능 — 1순위, 단계 분리

`is_recruiting`, 모집 기간, 모집 상태 필터, 일정 유형 '모집'까지 데이터는 이미 있다. 풀 지원서 시스템을 바로 만들지 않고 3단계로 나눈다.

### 1단계: 모집 공고 강화 (기존 데이터만으로 가능)

- 홈에 "모집 마감 임박" 섹션 노출
- 동아리 상세에 D-day 배지
- 모집 마감일 기준 정렬 옵션

### 2단계: 외부 지원 링크 (수요 검증용)

- 동아리 정보에 지원 링크 필드 1개 추가 (구글폼, 오픈채팅 등)
- 상세 페이지에 "지원하기" 버튼
- 회장 앱 동아리 정보 수정 폼에 필드 추가
- 클릭률로 자체 접수 기능 수요를 검증한 뒤 3단계 판단

### 3단계: 자체 지원서 접수 + 지원자 관리 (검증 후)

- 큰 공사. 일반 학생 계정 체계가 현재 없음 (회장/관리자 계정만 존재)
- 익명 접수 vs 학생 로그인 도입 결정이 선행돼야 함
- 2단계 지표가 나오기 전에는 착수하지 않는다

## 그 외 후보 기능 (효용 대비 비용 순)

| 기능 | 비용 | 비고 |
| --- | --- | --- |
| 일정 캘린더 구독 (ICS 내보내기) | 낮음 | 공개 일정 데이터 재사용, 엔드포인트 1개 |
| 총동연 대시보드 (보고서 제출 현황, 모집 중 동아리 수) | 중간 | 총동연 락인 + 타 학교 영업 무기 |

| 관심 동아리 찜 + 모집 시작 알림 | 높음 | 학생 계정/알림 인프라 필요, 3단계와 묶어서 진행 |

## 다른 학교 확장 준비

프론트 하드코딩은 적다. 학교 고유 값은 `apps/DONGLE-CLIENT/src/lib/site.ts`의 메타 문구 정도.

준비 순서:

1. **학교 고유 값 격리 (지금부터 습관)** — 새 기능에서 학교명, 분과 목록, 로고, 문구를 코드에 박지 않는다. 두 번째 학교 확정 전 멀티테넌트 추상화는 만들지 않는다.
2. **백엔드 스키마 협의 (진짜 관문)** — 모든 엔티티(clubs, users, banners, schedules)에 school/tenant 스코프 필요. 현재 API에 없음. 프론트보다 먼저 시작한다.
3. **URL 구조 결정** — 서브도메인(`scnu.dongle.kr`) vs 경로(`dongle.kr/scnu`). 서브도메인이 학교별 브랜딩·SEO에 유리, Next.js middleware로 처리 가능. 두 번째 학교 개발 착수 전 확정.
4. **역할 계층 추가** — 총동연 위에 서비스 운영자(여러 학교 관리) 역할 신설. 총동연 = 학교 단위 관리자로 재해석하면 기존 구조 대부분 재사용 가능.
5. **영업 관점** — 확장 병목은 코드가 아니라 각 학교 총동연 설득. "운영 조직이 편해지는 기능"(총동연 대시보드 등)이 영업 무기가 된다.

## 권장 실행 순서

1. 모집 공고 강화 + 외부 지원 링크 (1~2주 규모)
2. 백엔드 school 스코프 논의만 미리 시작
3. 두 번째 학교 확정 시 멀티스쿨 본격 착수
